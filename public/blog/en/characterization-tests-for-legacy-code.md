When you are handed a critical legacy subsystem with zero test coverage, zero documentation, and a mandate to refactor or replace it, your instinct might be to write clean, greenfield unit tests asserting how the system *should* work. This is a trap. If you write tests asserting ideal behavior, your refactoring will silently break downstream services that have adapted over years to the legacy system's quirks, bugs, and malformed schemas.

To safely touch legacy systems, you must use characterization tests (sometimes called Golden Master or Approval tests). The goal of a characterization test is not to assert correctness; it is to document actual, current behavior under a wide variety of inputs. If the legacy system outputs a malformed string or a negative balance due to an ancient bug, your characterization test must enforce that exact malformed string or negative balance as the pass condition. Only after the refactoring is complete can you deliberately choose to fix those bugs.

Here is how I build these safety nets before touching a line of legacy implementation.

## 1. Locating the Seams: Where to Intercept

Before you can write a characterization test, you must isolate the subsystem at a clean "seam"—a point in the codebase where you can observe and capture data flowing in and out without running the entire application stack. 

```
[ Input Data ] ---> [ SEAM: Input Capture ]
                          |
                  [ Legacy Subsystem ]
                          |
[ Downstream ] <--- [ SEAM: Output Capture/Golden File ]
```

If the legacy system communicates over HTTP or queries a database, do not spin up real databases or external APIs. Instead, intercept at these boundaries:
* **For HTTP/External APIs:** Use a tool like `msw` (Mock Service Worker) in Node, or `vcrpy` in Python, to record and playback the exact network payloads.
* **For Database Queries:** If you cannot easily mock the database driver, use a local, containerized sqlite or postgres instance initialized with a static snapshot of production-like schema and minimal seeds. 
* **For Pure Code Boundaries:** Write an integration wrapper that serializes inputs and outputs of the entry point function directly to disk.

## 2. Setting Up Golden Files and Avoiding Snapshot Noise

A common mistake when writing approval tests is capturing raw, serialized objects directly to a file. This leads to brittle tests that break due to irrelevant noise, such as transient timestamps, autogenerated database IDs, or system-specific file paths.

To make your golden files resilient:
1. **Scrub Nondeterminism:** Parse the output payload and replace volatile values (timestamps, UUIDs) with static placeholders (e.g., `"2020-01-01T00:00:00Z"` or `"[MOCKED_UUID]"`).
2. **Sort Collections:** If the legacy code returns SQL query results without an explicit `ORDER BY`, sort the array of objects by a stable key in your test harness before asserting. Databases do not guarantee row order.
3. **Prune Irrelevant Fields:** If you are refactoring a content transformer, discard system metadata fields like system memory usage or environment configurations.

## 3. Step-by-Step Example: Replacing a Legacy Content Transform

Let’s walk through a concrete scenario. You have a legacy content processing subsystem (`legacyTransform.ts`) that parses markdown-like syntax into a custom JSON structure. It is full of regex monsters, and you want to replace it with a modern parser. However, dozens of downstream rendering engines depend on its exact, idiosyncratic output.

### Step A: Write the Capture Harness

First, we create a test harness that runs the legacy code against a suite of input test fixtures, scrubs volatile fields, and compares the output to a stored JSON "golden file".

```typescript
import * as fs from 'fs';
import * as path from 'path';
import { legacyTransform } from './legacyTransform';

const FIXTURES_DIR = path.join(__dirname, 'fixtures');

// A helper to scrub dynamic noise out of the payload
function sanitizeOutput(rawOutput: any): any {
  const clean = JSON.parse(JSON.stringify(rawOutput));
  
  // Scrub dates or random IDs to prevent test flakiness
  if (clean.processedAt) {
    clean.processedAt = '2026-01-01T00:00:00.000Z';
  }
  if (Array.isArray(clean.nodes)) {
    clean.nodes = clean.nodes.map((node: any) => {
      if (node.id) node.id = 'node_constant_id';
      return node;
    });
  }
  return clean;
}

describe('Legacy Content Transform - Characterization', () => {
  const files = fs.readdirSync(FIXTURES_DIR).filter(f => f.endsWith('.input.txt'));

  test.each(files)('Fixture: %s', (inputFile) => {
    const inputPath = path.join(FIXTURES_DIR, inputFile);
    const goldenPath = inputPath.replace('.input.txt', '.golden.json');
    
    const rawInput = fs.readFileSync(inputPath, 'utf-8');
    
    // Execute current behavior
    const rawOutput = legacyTransform(rawInput);
    const actualSanitized = sanitizeOutput(rawOutput);

    // If the golden file does not exist, we write it (Record Mode)
    if (!fs.existsSync(goldenPath)) {
      fs.writeFileSync(goldenPath, JSON.stringify(actualSanitized, null, 2), 'utf-8');
      throw new Error(`Golden file created for ${inputFile}. Re-run tests to assert.`);
    }

    // Assert exact matches (Playback Mode)
    const expected = JSON.parse(fs.readFileSync(goldenPath, 'utf-8'));
    expect(actualSanitized).toEqual(expected);
  });
});
```

### Step B: Build your Input Matrix

Do not just test one "happy path" file. Put together an input matrix representing:
* **Standard cases:** Normal markdown strings with typical formatting.
* **Edge cases:** Nested lists, empty documents, inputs with raw HTML, emoji strings, and broken/unclosed tags.
* **Malicious/Broken inputs:** Huge strings (DoS vectors), SQL injection strings, and null bytes.

Run the test runner once with the legacy code to generate the initial batch of `.golden.json` files. Carefully review the generated golden files. Even if they contain obvious rendering bugs, **commit them as they are**. That is your baseline.

### Step C: Swap the Engine

Now, rewrite your content transformer using the clean, modern parser (`modernTransform.ts`). Swap the import in your characterization test:

```typescript
// import { legacyTransform as transform } from './legacyTransform';
import { modernTransform as transform } from './modernTransform';
```

Run your test suite. Your modern transformer will almost certainly fail on the first run. The test failures will point out exactly where your modern parser deviates from the old parser's behavior. 

Iterate on your modern implementation until the entire test suite passes. When it passes, you have strong empirical evidence that your new engine is a drop-in replacement for the legacy code across every edge case you captured. That is a demonstration over your recorded inputs, not a proof over all possible inputs — the strength of the guarantee is exactly the coverage of your golden file, which is why it is worth investing in capturing production traffic rather than hand-written samples.

## 4. When to Deliberately Update the Golden File

Characterization tests are not static forever. Once you have successfully completed your refactor without changing behavior, you can begin fixing long-standing bugs.

To fix a bug:
1. Write a standard, unit test asserting the *new*, correct behavior (e.g., asserting that unclosed HTML tags are closed properly).
2. Update the implementation to resolve the bug.
3. The characterization test will fail because the output now differs from the old, buggy golden master.
4. Verify that the diff in the golden file is *strictly* the bug fix you intended to introduce, and nothing else. 
5. Regenerate the golden file (e.g., delete the old `.golden.json` file and let your test runner rewrite it) and commit the updated golden file along with your change.
